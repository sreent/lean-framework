# Controls Catalogue

**Status:** Draft v0.1 · **Approved by:** the Head of Data, AI & Development · **Rules:** [Rulebook](rulebook.md)

How each rule is enforced, before and with the unified master data app (see
the [roadmap](roadmap.md)). The "With the unified app" column is what the app
must do. Controls change here as the app grows; the rules don't.

| Rule | Before the unified app | With the unified app | Evidence |
| --- | --- | --- | --- |
| R-01 Named owner | The GPDOs sign the charter and agree their domain profiles | Same | Signed charter, agreed domain profiles |
| R-02 Delegation | Delegations recorded in the domain profiles; the data governance specialist flags gaps and overlaps | Same | Agreed domain profiles |
| R-03 Governed process | Requests are raised in the current app; requests by email or spreadsheet are turned away | All requests go through the unified app. Non-SAP systems raise requests through its request interface. [TBC: on the app roadmap] | Request log |
| R-04 One system of record | Data flows from SAP over interfaces, and non-SAP copies hold the SAP key [TBC]. As each non-SAP system comes in, the data platform compares its copies with SAP and the consistency checker agent sorts the differences. | The same, plus checks in the interfaces or middleware that reject or quarantine bad records | Consistency scorecard |
| R-05 Checks before approval | Vendor checklist and SAP mandatory fields. The request pre-check agent reviews requests in the current app [TBC], and the duplicate finder flags likely duplicates. | The unified app's checks at entry: the domain's conventions and duplicate match rules, and checks such as VIES, IBAN and GTIN. Later, the request pre-check agent works inside the app on what fixed checks miss. | Check results stored with each request |
| R-06 Approval | Vendor maker-checker; turnaround in the vendor's reports | The unified app approves owner-approved request types automatically and routes the rest to the steward for each part they touch. The steward reviews a sample of automatic approvals each month. | Approval log, sample results |
| R-07 Mass changes | The data owner signs off by email [TBC]; tested in a non-production system first | Mass-change function in the unified app, with the sign-off built in | Sign-off and test evidence |
| R-08 Traceability | Only the master data vendor's staff hold SAP change rights, and they lose them for each request type as it moves. Each month, a report matches SAP change documents to requests in the current app, the change reconciler agent matches those with a missing or unclear reference, and [TBC: the internal controls team] reviews any change left without one. | Only the unified app's service identity holds change rights, and the app records the request on every change, so a daily report finds any change without one, for [TBC: the internal controls team] to review | Reconciliation report |
| R-09 Conventions and quality checks | The data platform runs the checks each domain profile defines on SAP data and publishes the scorecards monthly | Checks also run in the unified app at entry; scorecards update daily [TBC] | Scorecards |
| R-10 Fix at source, fix the cause | The quality triage agent groups failing records by cause and proposes new checks to the data owner; the vendor fixes the records in SAP | Each issue becomes a fix request in the unified app, raised by the quality triage agent | Issue log; checks added to the profile |
| R-11 Stale records | A monthly report on the data platform lists the records to block; the steward checks it, the owner approves it and the vendor blocks the records | The same, with the approval and the blocking done in the unified app | Approved list |
| R-12 Third parties | Vendor contract and [requirements](vendor-requirements.md); monthly performance review by the data governance specialist; exit plan in the [roadmap](roadmap.md) | No master data vendor. Any other third party works under the same terms. | Performance report, exit records |
| R-13 Sensitive changes | SAP sensitive-field settings block payment until the steward confirms the change, for example with FK08/FK09 for suppliers and FD08/FD09 for customers [TBC: confirm for your release]. Other sensitive changes, including credit limits and unblocking, are confirmed before the vendor enters them. SAP settings limit one-time accounts and payee in document. [TBC] | The app holds each sensitive change until the steward confirms it, never letting anyone confirm a change they requested or entered, then posts it to SAP. [TBC: whether this replaces SAP's own confirmation for changes the app posts, or SAP's stays on and needs a second confirmation] | Confirmation log |
| R-14 Payment data kept apart from paying | The platform team reviews the SAP roles of vendor staff and confirmers each quarter for conflicting rights [TBC: rule set] | The same, for confirmers and the unified app's service identity | Access review |
| R-15 Bank detail verification | The steward calls the supplier back on details already on file and records the call-back on the request; a report flags shared bank accounts | The unified app requires call-back evidence before confirmation, and checks the new bank account against every other supplier and customer when the change is entered | Call-back evidence, flag report |
| R-16 Classified fields and access | Data owners list their Confidential and Restricted fields in their profiles, approve the roles that can see them, and review who has access in SAP, and in other systems as their owners confirm them [TBC]; extracts of Restricted data need owner approval; data masked when SAP is copied to test systems [TBC: tool] | The same, with the unified app limiting who can see classified fields | Profiles, access reviews, approvals, masking log |
| R-17 Personal data lifecycle | [TBC: SAP Information Lifecycle Management end-of-purpose checks] | Same | Blocking and deletion log |
| R-18 Agents | [Agent register](operating-model.md#agents) kept by the data governance specialist; design review before go-live; logs kept as long as SAP change documents | An agent moves up a level on accuracy checked against an independent sample, and drops a level after a serious error. Changes to its model, instructions or tools are tested and re-approved. | Register, logs, sample results |
| R-19 Data team | Emergency access is logged and reviewed by [TBC: the internal controls team]; app and agent changes go through change management | Same | Review log, release records |
| R-20 Exceptions | Exception register [TBC: location] | Register in the unified app, which reminds owners before exceptions expire | Register |
| R-21 Trade secrets | Trade secrets marked in the domain profiles; the data owner reviews access in SAP and in the recipe systems and files that hold them [TBC]; kept off the data platform and out of extracts unless the owner approves; agents use AI models only in an environment the organisation controls [TBC] | The same, with the unified app limiting who can see trade secret fields | Access reviews, approvals, agent register |
| R-22 AI tools and data | Approved AI tools listed [TBC]; agents' instructions treat outside content as data; the owner's approval, and the data protection officer's for personal data, recorded before Confidential or Restricted data goes to an outside model | Same | Approved-tools list, approvals, agent register |
